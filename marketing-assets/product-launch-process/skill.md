# Product Launch Process

## Purpose

A launch fails when assets are made before the basics are settled: what the product is called, what it can be shown doing in each market, and what result counts as success. This skill builds the plan in that order, so every asset reuses one message and every claim matches a demo that works.

## Instructions

1. **Confirm the brief.** You need: what is launching (new product, feature or segment), which segments (regional banks, national banks, smaller banks) and use cases (lending, retail banking, bancassurance) and which markets (DACH, Benelux, Nordics). If any of these is missing, ask before planning. A launch "for everyone" can't be demoed or measured.
2. **Define.** Draft the messaging master from [`positioning.md`](../../knowledge-base/positioning.md): tagline, core premise, stage headlines, outcomes and one main illustration. Propose names that follow [`writing.md`](../../knowledge-base/design-system/writing.md) (literal feature names, sentence case, "moments" throughout). Say which tiers (Base, Ridge, Summit) the launch sits in and what upsell path it creates for existing customers.
3. **Prove.** Name 1–2 existing customers as pilot candidates and what the pilot should test. Propose launch KPIs with a target for each, split into early signs of traction (90 days) and business results. List every market × segment demo needed, and leave each one's rating as "to check": READY, PARTIAL or NOT READY is only set once the demo has been built and tried on local data.
4. **Enable.** List the sales assets (quick reference, deck via [`sales-deck-builder`](../../sales-tools/sales-deck-builder), demo playbook, market training, [`battlecard`](../../sales-tools/battlecard) updates) and the CSM and support assets (what changes for existing customers, FAQ, first-issue handling).
5. **Launch.** List the website, press release and partner co-marketing, user launch (in-app, email, blog, LinkedIn carousel) and event assets, each linked to the repo skill or design system that builds it.
6. **Learn.** Map every KPI from step 3 to where it's measured (CRM, Appcues, campaign reports, [`win-loss-analysis`](../../knowledge-base/win-loss-analysis), [`sales-call-analysis`](../../knowledge-base/sales-call-analysis)).
7. **Restrict claims to READY demos.** Any asset copy in the plan may only claim what a READY demo shows. Mark PARTIAL markets with what's missing.

## What to avoid

- Don't make assets before the messaging master exists. Every asset reuses it.
- Don't add dates or durations unless the user gives them. Timing depends on the product.
- Don't invent pilot results, customer quotes or KPI baselines. Leave them as gaps for the user to fill.
- Don't treat a market as READY because the product works there in theory. It's READY when a demo on that market's data has been built and tested.

## Output format

```
## Launch plan: [what is launching]

**Segments:** ...   **Markets:** ...   **Tiers:** ...

### 1. Define
Messaging master: tagline / premise / stage headlines / outcomes / illustration
Names: ...
Packaging and upsell path: ...

### 2. Prove
Pilot: [customers, what it tests]
Launch KPIs: | KPI | Target | Early or business result | Where measured |
Demo readiness: | Market | Segment | Rating (to check) | Missing |

### 3. Enable
Sales: ...   CSMs and support: ...

### 4. Launch
Website / Press and partners / Users / Events

### 5. Learn
Feedback sources mapped to KPIs

---
Open gaps for the user: ...
```
